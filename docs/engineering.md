# 开发与交付流程

Windows 保存源码和 Git；Debian WSL2 只运行可重建的 Linux 构建/测试。产品决策与发布依据来自本仓库。

## 阶段

| 阶段 | 输入 | 完成条件 |
| --- | --- | --- |
| 界定 | 对应需求、当前实现、失败场景 | 范围、保持不变的契约与验收检查明确 |
| 设计 | 用户可见的变化 | 原型可操作、内容/响应式检查完成、获得确切批准；非 UI 改动可跳过 |
| 实现 | 已确定契约 | 完整小切片，复用现有模块，不混入无关重构 |
| 验证 | 修改后的代码和实际构建 | 相关检查完成，结果与限制可追溯 |
| 交付 | 已验证内容 | 文档同步、聚焦提交、工作区状态清楚；发布另走发布流程 |

UI 使用项目本地 `prototype-first-ui` 与 `baoyu-design`。设计、批准和生产实现分别提交。
原型是界面规格，不是生产运行时；模拟数据、接口和成功反馈不能进入生产逻辑。
VitePress 文档页面直接维护本目录正文，不走产品 UI 原型门禁。

## 检查选择

| 改动 | 最小检查 |
| --- | --- |
| 文档 | 本地链接、事实、diff；操作命令改变时实际执行 |
| VitePress 站点 | `make check-docs`（构建、站内链接、搜索和移动布局） |
| 前端/共享契约 | `make frontend check-frontends`，再跑受影响 E2E |
| Hub/Agent | 对应 Rust 测试、fmt、Clippy；Linux 行为在 Linux 验证 |
| 存储 | 事务、精度、并发、恢复失败和迁移回归 |
| 打包/安装 | 相关脚本自测、工件验证；系统服务使用演练环境 |

Linux 命令经 `linux-task.ps1` 的 build 模式运行，使用相对路径。不向镜像复制 `.git`，不在镜像修补源文件。
Git-mutating 发布测试使用 Windows 临时仓库或一次性 CI。具体入口见 [测试](testing.md)。

## 提交与交接

使用 `type(scope): subject`。常用 type 为 `feat`、`fix`、`refactor`、`test`、`docs`、`build`、`chore`、`design`。
标题描述最终结果，正文按需要说明原因和验证。一个提交只有一个可解释的目的，不倒填作者、时间或虚构开发顺序。
默认分支为 `master`，普通功能分支使用 `codex/` 前缀。历史重建需要单独授权和仓库外恢复材料。
远端操作、发布和修改已发布资产不是普通代码修改的附带步骤。

交接只记录范围、分支/提交、实际检查和未完成项。任务聊天、提示词和临时计划不进入项目文档。
